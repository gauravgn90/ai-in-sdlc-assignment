● I drew the sequence diagram with the Mermaid MCP and wrote it up with a
  citation for each step. Neither file is committed yet.

  - Diagram: docs/architecture/approval-sequence.png
  - Write-up: docs/architecture/approval-sequence.md, which has the diagram

  The path

  1. Client: the Approve button runs decide() and then api() in
     app.js:72,82,16-19. That sends POST /api/approvals/{id}/approve with a
     Bearer token.
  2. SessionAuthMiddleware.InvokeAsync looks the token up with SessionStore.Get.
     If there is no session it returns 401. Otherwise it puts the session in
     HttpContext.Items.
  3. RequireRoleAttribute.OnActionExecuting checks the role is Approver or Admin
     (ApprovalsController.cs:9). If not, it returns 403.
  4. ApprovalsController.Approve gets the username with GetSession() and wraps
     the call in ApiControllerBase.Handle.
  5. ApprovalService.Approve works in this order:
     - It looks the invoice up through Find, which calls
       InMemoryInvoiceRepository.GetById. A missing invoice ends in 404.
     - EnsurePending checks the status. If the invoice isn't pending the request
       ends in 409.
     - It sets Status, DecidedBy and DecidedAt.
     - It calls InMemoryInvoiceRepository.Update, which takes a lock and
       replaces the list entry.
  6. Handle returns 200 with the invoice as JSON, with the status written as a
     string (Program.cs:10).

  Inferred, with no citation

  - Order of 401 and 403: this comes from the middleware order in Program.cs
    plus how ASP.NET Core runs middleware before filters, not from anything this
    repo states.
  - No 400 on approve: Handle catches ArgumentException, but Approve never
    throws one, so the diagram leaves that branch out.
  - Possible race (not tested): GetById hands back the stored object itself, not
    a copy. So ApprovalService changes the stored invoice before Update and
    outside the lock. Two approvals of the same invoice at the same moment could
    both pass EnsurePending. No test covers this.
  - Left out: the step where the framework creates ApprovalService for each
    request (Program.cs:15), and the UI's follow-up refresh(), which is a
    separate GET /api/invoices.

❯ I prefer option C instead. Should it be wise decision?                        

● Not on its own. Option C detects double and missed payments after they happen;
  it doesn't prevent them. For payments that matters, because a duplicate is
  money already sent, and you'd find out up to a day later and have to recover
  it by hand.

  Why the evidence argues against C alone

  - Unknown outcomes are routine, not rare. In one 90-minute window of INC-2041
    there are about 106 PayEx errors, including 100-second timeouts where we
    can't tell whether PayEx took the payment (app-logs.txt:179). With C, every
    one of those waits for the nightly run.
  - Users retry, and C does nothing to stop the second attempt. The pattern is a
    500 followed by a successful retry on another instance (INV-41360,
    INV-41454), and one invoice was approved four times (INV-41340). The 2.14.3
    retry policy adds automatic retries on top. Under C, each of those can
    become a second payment.
  - Failures cluster at month-end (INC-2041 README:28). That's when
    reconciliation finds the most problems and finance has the least time to fix
    them.
  - C needs something from PayEx we haven't confirmed. Nightly reconciliation
    needs a way to list or query PayEx payments by our reference, and nothing in
    ops/ shows PayEx has one. Without it, C can't be built at all.

  When C is a reasonable choice

  - Volume is low, so a day's mismatches can be fixed by hand.
  - Finance agrees that a duplicate that sits for up to 24 hours and is refunded
    manually is acceptable.
  - PayEx has a list or report API we can match against.
  - It's an interim step with a date to move to something stronger.

  If you go with C, add these two things

  They're cheap and remove most of the duplicate risk without an outbox:

  1. A unique PaymentSubmission(InvoiceId) row, written before calling PayEx. If
     the row already exists, don't call PayEx again; return its current state.
     This blocks the second attempt from retries, double-clicks and other
     instances. It's about one table and a dozen lines.
  2. A stable idempotency key or reference on every PayEx call, with no 
     automatic retry on timeout. Mark the payment Unknown and let reconciliation
     settle it. Disable the 2.14.3 retry policy for this call unless PayEx
     deduplicates.

  Those two additions are option A, done in the request. A plus C is a
  defensible choice: much simpler than an outbox, with prevention for the common
  case and reconciliation as the backstop. What it leaves unsolved is that
  approvals still slow down or fail when PayEx does, which was the INC-2041
  failure itself.

  My answer: C alone is not a wise choice for payments. A plus C is a
  reasonable, lower-cost choice if finance accepts next-day detection for the
  remaining unknown outcomes. Either way, first confirm what PayEx supports: an
  idempotency key, lookup by reference, and a list or report API.
